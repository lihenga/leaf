## 先抓住主线

大模型生成文本时，通常要确定上一个 token，才能继续生成下一个。推测解码让一个便宜的草稿生成器先猜后面几步，再让目标模型批量检查；如果猜对了一段，就能减少目标模型反复执行的轮数。

MTP 可以提供这样的草稿，但它首先属于训练设计。DSpark 进一步考虑两个问题：并行猜出的后几个 token 怎样保持连贯，以及当前系统负载下究竟值得检查几个。

理解这条路线，始终要把三件事放在一起看：**草稿生成成本、连续被接受的长度、目标模型验证成本**。原帖的主要价值，是把不同方法放回这三个量之间的取舍中。

## 1. 为什么明明有 GPU，还要逐个生成？

Token 是模型处理文本的基本单位，可能是一个字、一个词的一部分或标点，并不固定对应一个汉字。自回归生成用已经确定的 token 预测下一个 token。

后文会用到几个工程术语：一次 forward 是模型执行一次前向计算；logits 是转换成概率之前的词表分数；backbone 是承担主要计算的主干网络；head 是接在其上的预测模块。KV Cache 缓存先前 token 的 attention 键和值，避免每一步从头计算已有上下文。

训练或处理已有 prompt 时，整段输入已知，可以并行计算多个位置。生成时，未来输入尚未确定：如果上一位置最终选择了另一个词，后续的条件就改变了。

但“不能提前确定未来”不等于“不能同时检查一段已给出的候选”。一旦草稿提供候选序列，目标模型就能用因果掩码，在一次前向计算中得到多个位置的预测分布。因果掩码保证每个位置只依赖它前面的内容。

这里可能有硬件收益：低并发 decode 往往没有用满计算能力，而模型权重每轮仍要参与计算。让同一次执行处理几个验证位置，可能比逐个执行划算。额外位置仍有计算和 KV 读写成本，高并发时也会占用其他请求需要的容量。

## 2. 一轮推测解码发生了什么？

下面是自编的示意，字母仅代表 token，不是真实模型输出：

```text
已确认前缀
    ↓
草稿提出：A → B → C → D
    ↓
目标模型一次计算各位置的条件分布
    ↓
从左到右决定是否接受
    ├── A、B 通过，C 被拒绝：提交 A、B 和替代 C 的补偿 token
    │                       D 作废，下一轮重新生成
    └── 全部通过：提交 A、B、C、D，再加一个目标模型生成的 token
```

为什么 C 失败后不能保留 D？因为验证 D 时使用的上下文包含草稿 C，而实际提交的是另一个 token。条件已经变了，原来的 D 不能直接复用。

全部通过时多出的一个 token 通常叫 **bonus token**。因此，报告“每轮接受长度”时，要先说明是否包含这个额外 token。

### Greedy 与 sampling 的接受规则不同

Greedy 每次选概率最大的 token。验证时比较草稿与目标模型的选择，遇到第一次不一致便停止。

Sampling 会按概率随机采样，不能只检查“草稿答案是否看起来合理”。记目标分布为 $p$、实际草稿分布为 $q$，标准算法以以下概率接受候选 $x$：

$$
\alpha(x)=\min\left(1,\frac{p(x)}{q(x)}\right).
$$

拒绝时，从归一化后的 $\max(0,p-q)$ 残差分布中抽取补偿 token。直观上，草稿过多提议的部分要被削掉，提议不足的部分则由补偿采样补回来。这是保持目标分布的关键；详见[原始推测解码论文](https://arxiv.org/abs/2211.17192)。

**补充演算：** 假设只有 A、B，目标概率是 `(0.6, 0.4)`，草稿概率是 `(0.8, 0.2)`。A 的接受率是 `0.6/0.8=0.75`，B 的接受率是 1。草稿提出 A 后被拒绝的总概率为 `0.8×0.25=0.2`，残差全部补给 B。最终 A 的概率是 `0.8×0.75=0.6`，B 是 `0.2+0.2=0.4`，回到目标分布。

这里的 lossless 指分布保持；随机采样两次不必生成逐字相同的文本，也不意味着能修复目标模型原本的错误。

## 3. MTP 在这条链路里处于什么位置？

**Multi-Token Prediction 是让模型在训练时学习预测多个未来位置。** 额外预测任务可以帮助共享表示学习；保留相应模块时，也可能用它们生成推理草稿。[MTP 原始论文](https://arxiv.org/abs/2404.19737)给出的是共享主干、多个独立预测头的设计。

| 概念 | 回答的问题 | 能否单独存在？ |
| --- | --- | --- |
| MTP | 模型训练时还学习预测哪些未来位置？ | 可以只作辅助训练，推理时不用额外头 |
| 推测解码 | 怎样提案、验证并提交多个 token？ | 可以用独立小模型等候选源，不依赖 MTP |

不同 MTP 结构不完全相同，不能把所有方法都理解成互不交流的并行头。共同的边界是：**能预测多个未来位置，不代表可以跳过目标模型验证直接提交。**

## 4. 草稿生成器为什么不断变化？

可以沿两个独立维度理解：一是候选怎样生成，二是候选怎样组织。链与树属于组织方式；自回归与并行属于生成依赖，二者不是互斥的分类。

| 路线 | 获得什么 | 付出什么 |
| --- | --- | --- |
| 自回归草稿，如独立小模型或 EAGLE 路线 | 后面的候选知道前面实际选择了什么 | 草稿也需要顺序执行，越长越慢 |
| 多个并行预测头，如 Medusa | 一次得到多个未来位置的候选 | 远端位置不直接知道前面采样结果，组合可能不连贯 |
| 并行 block，如 DFlash | 把主要草稿计算合并到一次执行 | 后缀仍可能出现条件不一致 |
| 半自回归，如 DSpark | 大部分计算并行，再用轻量顺序模块补依赖 | 增加少量串行工作，还要管理验证预算 |

候选树提供多条可能续写，让验证覆盖分支不确定性；树越大，目标模型检查的节点也越多。能覆盖更多可能性，不保证每秒能提交更多 token。

## 5. DSpark 的两个设计怎样配合？

对照[DSpark 论文第 3 节](https://arxiv.org/html/2607.05147v1#S3)，可以把它理解成生成和调度两层改进：

1. 较重的 backbone 并行给出整个 block 的基础预测，轻量顺序 head 根据已采样 token 修正后续 logits。默认 Markov head 只补相邻依赖，并未恢复完整自回归草稿的全部历史建模。
2. 置信度模块估计各位置被接受的概率，调度器结合前缀存活率和引擎的性能曲线，选择本轮验证长度。

**补充例子：** 若前三个位置“前面都已通过时，自己也通过”的概率依次为 `0.9、0.8、0.5`，连续存活到这三个位置的概率就是 `0.9、0.72、0.36`。第三个候选本身即使有一定把握，只有前两关也通过，才产生实际收益。

调度因此要比较：多检查后缀的预期收益，是否值得它占用的 batch 容量。忙碌时可能缩短，空闲时可能放长。草稿已经生成的长度，与最终拿去验证的长度，可以不同。

动态选择还必须遵守概率算法的条件，不能偷看后续抽样结果，再倒过来选择前面的候选，否则可能引入选择偏差。置信度高也不能代替目标模型的正式验证。

## 6. 怎样判断这套东西有没有真正加速？

定义一轮提交的 token 数为 $\tau$，包含补偿或 bonus token，则一个便于理解的平均成本模型是：

$$
L\approx\frac{T_{draft}+T_{verify}+T_{other}}{\tau}.
$$

**自编算例，非论文实测：** 普通 decode 每 token 要 4ms。推测方案一轮草稿 1ms、验证 3ms、其他开销 0.5ms，平均提交 3 个 token，则约为 `4.5/3=1.5ms/token`。如果同样一轮只提交 1 个，便成了 `4.5ms/token`，反而比基线慢。

实际评估至少需要同时看：

- 每个位置的条件接受率与每轮提交数，明确是否包含 bonus。
- Draft、Verify、采样、调度与 KV 提交或回滚的分别耗时。
- 相同硬件、模型、精度、上下文长度和请求负载下的端到端结果。
- 单用户速度、整机吞吐与 P99 延迟，避免只看 batch=1 的漂亮数字。

原帖引用的 DSpark 性能结果属于论文特定部署条件；本记录没有复现实验，也不据此推断其他引擎能获得相同比例的收益。

## 7. 读完后怎样用到工程判断中？

以下是整理者的延伸判断。

如果要评估一个推测解码实现，第一步应确认瓶颈在哪。目标 decode 已被其他请求充分填满时，额外验证位置可能很贵；草稿耗时占比很高时，仅增加接受长度未必划算。

状态管理也会决定算法能否落地：被拒绝的候选不能污染正式 KV Cache，树的 attention mask 必须隔离兄弟路径，变长验证也需要执行布局真正减少工作量。只在调度器里缩短长度、底层仍补齐到最大长度，未必节省计算。

**带走的问题：当前限制系统的是猜不准、猜得慢，还是检查得太多？** 这比先选一个方法名更能指导下一步测量。
