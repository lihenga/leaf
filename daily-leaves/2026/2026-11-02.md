## 先抓住主线

这项实验给语言模型增加了一组由编译器生成的权重，用前向计算执行处理器逻辑，并用模型的循环状态保存运行数据。Qwenputer 实现了 CPU，QwenPU 又加入向量单元，让一个很小的语言模型能够作为程序，在这台“内部计算机”上运行。

最值得理解的是三者的分工：**权重承载计算规则，运行时状态承载程序与数据，驱动负责启动和组织执行。** 这样才能看清“计算机在模型里”具体是什么意思，而不会把它误读成模型突然学会了任意精确计算。

## 1. 先区分两种做计算的方法

通常，语言模型接到一道计算题，会生成一段可能正确的文本。也可以让它调用外部 Python：模型发出请求，解释器执行，再把结果交回模型。

这里探索的是另一种实现位置：让神经网络中一部分经过专门构造的计算，承担处理器的状态转移。它仍然运行在 GPU、推理软件和驱动之上，但加法、访存等逻辑不再交给一个外部解释器完成。

用一个补充类比理解：普通神经网络的参数大多由训练学到；这个实验则像把一份“电路图”按规则翻译成神经网络参数。每一步输入和状态确定之后，这部分电路就按构造好的规则工作。

这里的“不需要训练”只针对新增的计算机权重。Qwen 底座和里面运行的小语言模型，当然都有各自的训练过程。

## 2. 计算机的内存从哪里来？

Gated DeltaNet 是会逐步更新并保留状态的一类网络层。[Qwenputer 项目说明](https://github.com/divagr18/qwenputer#gated-deltanet-as-ram)介绍了它对这类状态的利用：把衰减关掉，用 one-hot（只有一个位置为 1）的地址选定一行，并以完整写入强度覆盖该行；读取时用相应查询取回那一行。这样，状态矩阵就能充当可寻址存储。

**补充的简化模型：** 假设状态矩阵 $S$ 有很多行，$k$ 是只在第 $i$ 个位置为 1 的地址向量，$v$ 是要存的值。忽略其他实现细节，一次覆盖可写成：

$$
S' = S + k\left(v^T-k^TS\right).
$$

因为 $k$ 只选中一行，更新后第 $i$ 行变成 $v^T$，其余行保持原状；$k^TS'$ 则读出该行。这是帮助理解寻址的代数示意，不是项目完整的张量布局。

关键区别在于：这些运行数据保存在状态里，而非每写入一个字节就修改模型权重。

## 3. CPU、程序与语言模型怎样连接？

原帖介绍的 Qwenputer，使用编译出来的网络层执行 RISC-V 指令逻辑。RISC-V 是指令集规范；在这里，它定义这台虚拟处理器怎样算术、访存和跳转。

可以把执行路径整理成下面这张图。图是整理者对架构的简化，不表示所有步骤只消耗一个 token：

```text
语言模型提出计算请求
        ↓
内部调用桥接与固件
        ↓
编译进权重的 CPU 逻辑
        ↕
DeltaNet 状态：程序、寄存器、内存等运行数据
        ↓
执行结果回到语言模型的上下文
```

执行过程中会出现 trace token，用来编码地址、值和步骤等信息。它们相当于内部执行轨迹，不能与用户最终看到的文字 token 混为一谈。

原帖中“没有外部 runtime”的说法需要限定：项目依然有 `RvChat` 驱动加载固件、管理状态和处理内部轨迹。准确理解是，CPU 的运算由编译网络执行，而不是靠外部 Python 替它计算；并不是下载权重后就不再需要任何软件配合。[项目的启动与调用说明](https://github.com/divagr18/qwenputer#quickstart)也明确写出了驱动的职责。

## 4. QwenPU 又增加了什么？

CPU 能执行通用指令，但用大量细碎指令完成神经网络矩阵运算，轨迹会非常长。QwenPU 加入专门的向量单元，把成组的数据运算变成更直接的操作。

向量单元有自己的状态存储，提供矩阵运算、量化、逐元素操作、attention 相关计算和数据搬运等功能。[向量单元设计文档](https://github.com/divagr18/QwenPU/blob/main/docs/vx.md)强调，操作的读写、计算深度与逐 token 语义需要相互匹配。

项目演示运行的是 stories260K：一个约 26 万参数的小型 Llama。它作为 C 程序运行，模型参数以数据形式加载进内部存储。这里有两个不同角色：外层网络提供执行计算机的结构，内层小模型提供要执行的神经网络任务。

因此，“模型里运行另一个模型”是一个明确的执行关系，并不表示 Qwen 通过阅读文字就自行模拟出了另一个模型的全部行为。

## 5. 演示结果该怎样读？

[QwenPU README](https://github.com/divagr18/QwenPU)给出的故事生成开销如下。数字是作者报告，不是本仓库复现：

| 实现 | 每生成一个 story token 所需 trace token |
| --- | ---: |
| 普通 C 路线 | 2,430,000 |
| Qwenputer NPU 路线 | 225,000 |
| QwenPU 向量单元 | 53,000 |

首尾相除约为 **46 倍的轨迹数量缩减**，不是 100 倍，也不能直接当成墙钟时间加速比。README 报告 L4 上生成一个 story token 约需 16 秒，说明它目前仍有很高的执行开销。

同一份说明给出的完整 bf16 checkpoint 为 26.7GB，整体加载需要至少 40GB GPU；只运行计算机层的故事演示与检查则可放入 24GB GPU。两种运行方式应分开理解。

原帖还引用了 Qwenputer 的算术成绩。那是特定任务、版本与评测配置的结果，不能扩大成“此后所有数学题都能答对”。

## 6. “每一步精确”究竟保证什么？

精确执行首先是指编译电路与指定参考机器语义相符。即便这一层完全正确，端到端答案还可能出错：

- 用户的问题被理解错，模型选错算法或程序。
- 固件或程序本身写错，处理器只是精确地执行了错误程序。
- 整数位宽、定点运算或量化语义，与使用者期待的实数运算不同。
- 计算结果正确，后续自然语言解释却又添入错误。

所以，处理器轨迹匹配参考实现，与“模型所有输出都可信”是不同层次的结论。项目测试报告能支持其覆盖范围内的执行一致性，无法自动证明上面所有环节。

## 7. 为什么这项实验值得关注？

以下是整理者的延伸判断。

它提供了一个很具体的观察窗口：同一套模型执行结构里，哪些部分是学习得到的语言行为，哪些部分可以按规则构造并逐步检查。对理解混合架构、状态记忆和神经网络中的算法执行，这比单纯追问“模型会不会算数”更有启发。

但内部执行也有代价。外部工具可以独立升级和扩容；把功能编译进网络后，版本、状态接口、驱动和执行性能都需要一起考虑。是否更适合某个产品，应比较完整成本，而不只比较工具是否位于模型边界以内。

阅读类似项目时，可以继续问三件事：

1. **规则放在哪里，数据放在哪里？** 分清权重、循环状态与执行轨迹。
2. **证明或检查的是哪一层？** 是指令执行一致，还是最终任务答对？
3. **展示能力与实际成本是否同时给出？** 轨迹数量、耗时、显存和运行方式都影响可用性。
